ตรวจสอบงานตามระดับความเสี่ยงที่ user เลือก — เป้าหมายคือบอกให้ชัดว่าตรวจอะไรแล้ว อะไรยังไม่ได้ตรวจ ไม่ใช่รับประกัน 100%

> **L1 ไม่อยู่ใน skill นี้** — L1 คือการ verify ตามกฎใน `SOUL.md` ("ก่อนแจ้งว่าสำเร็จ ต้อง verify") ที่ Ava ทำทุกงานอยู่แล้ว skill นี้มีเฉพาะ L2 / L3 สำหรับงานที่ต้องตรวจเพิ่ม

---

## ขั้นที่ 1 — ระบุงานที่จะตรวจ

argument ที่รับมา: `$ARGUMENTS`

- มี argument → ใช้เป็นงานที่จะตรวจ
- ไม่มี argument → สรุปงานล่าสุดในบทสนทนา (สิ่งที่เพิ่งทำหรือกำลังคุยอยู่)
- ระบุงานไม่ได้ → ถาม user ว่าจะตรวจงานไหน แล้วหยุดรอคำตอบ

รวบรวมข้อมูลของงาน:

1. **โจทย์เดิม** — user ต้องการอะไร + เกณฑ์ที่ถือว่าสำเร็จ
2. **ขอบเขต** — ไฟล์ที่เกี่ยวข้อง (ใช้ `git diff HEAD --stat` ถ้าเป็นงาน code) หรือเนื้อหาในบทสนทนา (ถ้าเป็นเอกสาร)
3. **ประเภทงาน** — เช่น code การเงิน, สัญญา/กฎหมาย, ข้อมูลส่วนบุคคล, migration, logic ทั่วไป

---

## ขั้นที่ 2 — ถามระดับการตรวจ

ใช้ `AskUserQuestion`:

- **header:** `ระดับตรวจ`
- **question:** `[สรุปงาน 1 บรรทัด] — ควรตรวจระดับไหน?`
- **options:** (ระดับที่แนะนำอยู่ลำดับแรก + ต่อท้าย label ด้วย `(แนะนำ)` + ใส่เหตุผลใน description)
    - `L2 สำคัญ` — ตรวจผลจริง + edge case + breaking changes + test suite ของโมดูล
    - `L3 วิกฤต` — L2 + checklist เฉพาะด้าน + ผู้ตรวจอิสระ (ใช้ token มากขึ้น)

**แนวทางแนะนำระดับ:**

| ระดับ | งานลักษณะ |
|---|---|
| L3 | เงิน ภาษี ดอกเบี้ย, สัญญา/กฎหมาย, ข้อมูลส่วนบุคคล |
| L2 | logic หลัก, migration, auth/security, ลบหรือ overwrite ข้อมูล, เปลี่ยน public API |
| (L1) | ที่เหลือ — ไม่ต้องใช้ skill นี้ |

งานไม่เข้าเกณฑ์ L2 / L3 → แจ้ง user ว่า verify ปกติ (L1) ทำไปแล้ว พร้อมหลักฐาน แล้วใช้ `AskUserQuestion` ถามว่า `ตรวจ L2 ต่อ` หรือ `❌ ยกเลิก`

## ขั้นที่ 3 — วาง checklist ให้ user อนุมัติ

สร้าง checklist จาก **ระดับ + ประเภทงาน** โดยเลือกเฉพาะข้อที่เกี่ยวกับงานนี้จริง (ไม่ต้องใส่ทุกข้อในคลัง)

### คลัง checklist

**L2 (ทุกงานที่ใช้ skill นี้)**
- รัน code / test ที่เกี่ยวข้อง หรืออ่านไฟล์ที่แก้ทวนซ้ำ
- ผลลัพธ์ตรงกับโจทย์เดิม
- test edge case: ค่าว่าง, null, ค่าขอบ, input ผิดรูปแบบ
- breaking changes: ไฟล์อื่นที่เรียก function/API ที่แก้
- รัน test suite ทั้งชุดของโมดูลนั้น

**L3 — 💰 Code การเงิน**
- ใช้ `Decimal` หรือหน่วยสตางค์เป็นจำนวนเต็ม ห้าม `float`
- กำหนดการปัดเศษชัดเจน (วิธีปัด + ปัดที่ขั้นตอนไหน)
- test: 0, ติดลบ, ค่าสูงมาก, ปัดเศษที่ .5
- idempotent — เรียกซ้ำแล้วไม่ตัดเงิน/บันทึกซ้ำ
- ยอดรวม balance (เดบิต = เครดิต)
- timezone ตอนตัดรอบวัน/เดือน
- transaction rollback เมื่อขั้นตอนใดล้มเหลว

**L3 — 📜 สัญญา / กฎหมาย**
- คำนิยาม ตัวเลข วันที่ ชื่อคู่สัญญา ตรงกันทั้งฉบับ
- การอ้างเลขข้อถูกต้อง ไม่มีข้อที่ขัดกันเอง
- ตัวเลขที่เขียนเป็นคำกับตัวเลขตรงกัน
- แยกรายการข้อที่เสี่ยงหรือคลุมเครือ
- แนบคำเตือน: ไม่ใช่คำปรึกษาทางกฎหมาย งานที่มีผลผูกพันต้องให้ผู้เชี่ยวชาญตรวจ

**L3 — 🔐 ข้อมูลส่วนบุคคล**
- ไม่ log / print ข้อมูลส่วนบุคคล
- เช็ค authorization ทุก endpoint ที่เข้าถึงข้อมูล
- mask ข้อมูลในหน้าจอและ error message

**L3 — ประเภทอื่น** → สร้าง checklist เฉพาะด้านตามความเสี่ยงของงานนั้น

### แสดงและอนุมัติ

แสดง checklist เป็นรายการมีเลขข้อ (ระบุระดับ + ประเภทงานด้านบน) แล้วใช้ `AskUserQuestion`:

- **header:** `Checklist`
- **question:** `ใช้ checklist นี้ตรวจเลยไหม?`
- **options:**
    - `✅ ตรวจตามนี้` — เริ่มตรวจ
    - `✏️ แก้ checklist` — เพิ่ม / ลบ / แก้ข้อ
    - `❌ ยกเลิก` — ไม่ตรวจ

- เลือก `✏️` → ให้ user พิมพ์สิ่งที่ต้องการแก้ → อัปเดต → แสดงใหม่ → ถามซ้ำจนอนุมัติ
- เลือก `❌` → หยุด

## ขั้นที่ 4 — ตรวจ

### L2

ตรวจทีละข้อด้วยตัวเอง — รัน / อ่านจริงทุกข้อ ห้ามสรุปจากความจำ

### L3

1. ตรวจข้อ L2 ด้วยตัวเองก่อน
    - **ทำงานคู่กับ superpowers:** ถ้า code ชุดเดียวกัน (commit range เดียวกัน และไม่มีการแก้หลังจากนั้น) ผ่าน final review ของ superpowers ใน session นี้แล้ว → ข้อ L2 ทั่วไปอ้างผล review นั้นเป็นหลักฐานได้ ไม่ต้องตรวจซ้ำ แต่ข้อ 2 ยังต้องทำ: ส่งให้ผู้ตรวจอิสระเฉพาะ checklist เฉพาะด้านของ L3 (final review ของ superpowers ไม่ได้ใช้ checklist เฉพาะด้าน)
2. ส่งข้อ L3 ทั้งหมดให้ผู้ตรวจอิสระด้วย `Agent` tool:
    - **subagent_type:** `ava-claude-plugins:ava-validator`
    - **prompt:** ประกอบตามโครงด้านล่าง

```
## บทบาท
[ผู้เชี่ยวชาญที่ตรงกับประเภทงาน เช่น "Auditor ระบบการเงิน เน้นความถูกต้องของยอดเงินและการปัดเศษ"]

## โจทย์เดิม
[สิ่งที่ user ต้องการ + เกณฑ์ที่ถือว่าสำเร็จ]

## ขอบเขต
[path ของไฟล์ / คำสั่ง git diff ที่ใช้ดู / เนื้อหาเอกสารฉบับเต็มถ้าไม่ได้อยู่ในไฟล์]

## Checklist
[ข้อ L3 ที่ user อนุมัติ พร้อมเลขข้อ]

## กฎเฉพาะงาน
[convention ของโปรเจกต์ / ข้อกำหนดทางธุรกิจที่เกี่ยวข้อง — ไม่มีให้เขียน "ไม่มี"]
```

**ห้ามใส่ใน prompt:** เหตุผลหรือการตัดสินใจระหว่างที่เขียนงาน — ผู้ตรวจต้องตัดสินจากผลงานจริง ไม่คล้อยตามผู้เขียน

### เจอ 🔴 ต้องแก้

ใช้ `AskUserQuestion`:

- **header:** `ผลตรวจ`
- **question:** `พบ 🔴 [n] จุด — แก้เลยไหม?`
- **options:**
    - `🔧 แก้เลย` — แก้ทุกจุด 🔴 แล้วตรวจซ้ำเฉพาะจุดนั้น
    - `📋 รายงานอย่างเดียว` — ไม่แก้ ส่งรายงาน

**กฎกันงานค้าง:** แก้ได้ **1 รอบ** — ตรวจซ้ำแล้วยังเหลือ 🔴 → ส่งรายงานพร้อมจุดที่ค้าง ไม่วนแก้ต่อ

## ขั้นที่ 5 — รายงาน

```
🏷️ ระดับ: L[2|3] — [ประเภทงาน]

| # | Checklist | ผล | หลักฐาน |
|---|-----------|----|---------|
| 1 | ... | ✅ / 🔴 / 🟡 / ⚠️ | file:line / output |

✅ ตรวจแล้ว: [n ข้อ — ผ่าน n]
⚠️ ยังไม่ได้ตรวจ: [ข้อที่ตรวจไม่ได้ + เหตุผล]
🔍 ผู้ตรวจอิสระ: [🔴 n / 🟡 n — แก้แล้ว n] (L3 เท่านั้น)
🎯 ความเสี่ยงที่เหลือ: [จุดที่ user ควรดูเอง]
```

- "ยังไม่ได้ตรวจ" ห้ามว่าง — ตรวจครบจริงให้เขียน "ไม่มี" พร้อมเหตุผล
- ห้ามสรุปว่า "ผ่าน" ถ้ายังมี 🔴 หรือ ⚠️ ค้าง
